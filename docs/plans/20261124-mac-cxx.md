# C++ for macOS targets

`CXX_<t>` and cmake's C++ for `aarch64-apple-darwin` and `x86_64-apple-darwin` on Linux and Windows hosts, so that crates such as boring-sys, librocksdb-sys, libduckdb-sys and cxx build there and their binaries run on macOS.

## Approach

macOS's own libc++, linked as Xcode links it, rather than a static libc++ compiled from source on the first C++ compile, as Zig does: nothing to compile, the binary loads `/usr/lib/libc++.1.dylib` as an Xcode build does, and the headers' availability marks fail what the deployment target's libc++ lacks at compile time, as Xcode's do.

- Headers and lists of exports from LLVM 20.1.8's release, `libcxx-20.1.8.src.tar.xz` and `libcxxabi-20.1.8.src.tar.xz` (5 MB), not Zig 0.17.1's libc++ 22: its headers fail on clang 18 and 19 (`__builtin_clzg`, `__GCC_DESTRUCTIVE_SIZE`), and clang 18 is `ubuntu-latest`'s and Ubuntu 24.04's. libc++ 20 takes clang 18 and newer, and macOS 10.12 and newer.
- The stubs, `usr/lib/libc++.tbd` (install name `/usr/lib/libc++.1.dylib`) and `usr/lib/libc++abi.tbd`, list what `libcxx/lib/abi/<arch>-apple-darwin.libcxxabi.v1.stable.exceptions.nonew.abilist` says the dylib exports for each arch. libc++abi's own, which it re-exports (type `I`), are in libc++abi's stub, which libc++'s re-exports, so that ld64.lld binds them to `/usr/lib/libc++abi.dylib`, as Xcode's SDK does below macOS 15.4: an older libc++ re-exports only a list of them, without `typeid(__int128)`'s, say. No file of Apple's.
- `__config_site` as Apple's build writes it (`libcxx/cmake/caches/Apple.cmake`), with the vendor's availability marks on, but for what those lists lack: no time zone database, the parallel algorithms serial rather than on libdispatch.

## Steps

- [x] Probe: a C++ program (iostream, exceptions, threads, regex, shared_ptr, dynamic_cast) built against such an SDK by this Mac's clang 21 and by Ubuntu 24.04's clang 18 in Docker, linked by `ld64.lld`, runs here on arm64 and on x86_64 through Rosetta; `std::to_chars` of a double fails to compile below macOS 13.3 and builds from it, as with Xcode.
- [x] `DARWIN`: libc++'s headers in `usr/include/c++/v1/` (not `__cxx03/`, which only a define of the user's takes), libc++abi's two, the assertion handler and the two lists; `sdk` writes `__config_site` and `libc++.tbd` in place of the lists.
- [x] The wrapper as clang++ for Apple: g++'s driver and `-stdlib++-isystem <SDK>/usr/include/c++/v1`, as clang takes the headers beside itself first (a distro's libc++ for Linux). clang++ links `-lc++` itself, and rustc gets `-lc++` from cc; the SDK has the stub. A user's `SDKROOT`, Xcode's, has its own.
- [x] `CXX_<t>` for Apple's targets, and the wrapper as cmake's C++ compiler.
- [x] The wrapper passes `-mmacosx-version-min` last: the last one it's given, else `MACOSX_DEPLOYMENT_TARGET`, at least 11.0 on arm64. clang on Linux takes no variable (10.4 with no flag), and raises arm64's 10.12 only for the link, so the headers allowed `std::atomic::wait` (macOS 11) at 10.12.
- [x] Unit tests: the SDK's layout, the stub, the C++ flags.
- [ ] tests/cxx for Apple's targets: built on Linux and Windows, run on `macos-latest`, x86_64 through Rosetta. `std::format` needs macOS 13.3 (any use instantiates its float formatting, `std::to_chars`), so on macOS the test formats with iostream.
- [ ] boring, rocksdb and duckdb through `crates.yml` for each Apple target; curl and git2 need frameworks, as before.
- [x] readme, how-it-works, agents.md, help, roadmap.

## Not here

- Frameworks, as before: the user's `SDKROOT` or a macOS runner.
- What a newer macOS's libc++ has that LLVM 20's lists lack: the headers mark LLVM 21's and 22's as unavailable anyway.
- `std::pmr` (macOS 14) and `std::bad_optional_access` (10.13), which neither LLVM 20's headers nor Xcode's mark: they compile for an older macOS and fail there to load.
- A C++ library linked statically, as Zig's: an Xcode build loads the system's too.

# Apple's targets from Linux and Windows

Done: 2026-11-16, PR #5

`aarch64-apple-darwin` and `x86_64-apple-darwin` set up by cargo-solo on a Linux or Windows host, the minimal case: Rust, C through `cc`, no frameworks. On a Mac they still go to cargo as is.

The SDK's part a link needs is in Zig's source: `lib/libc/darwin/libSystem.tbd`, the text stub of libSystem for both arches, and `lib/libc/include/any-darwin-any/`, macOS's headers. Zig itself never runs.

## Steps

- [x] `Libc::Darwin` and `DARWIN`: two parts of Zig 0.17.1's source tarball (23 MB), pinned by SHA-256, from ziglang.org and a community mirror Zig lists, laid out as Xcode's SDK is: `usr/include/`, `usr/lib/libSystem.tbd`. Not Zig's `SDKSettings.json`: it lacks `MaximumDeploymentTarget`, and clang warns of it on every file.
- [x] `fill`: the parts of one file share its download; an SDK gets libSystem's aliases (`libc.tbd`, `libm.tbd`, …) and our own `libiconv.tbd` stub, which the libc crate links.
- [x] The two targets, one sysroot folder for both (`macos-<hash>`), as `SDKROOT` names one; on a Mac neither is ours, nor in the help.
- [x] Flags: `--target=arm64-apple-macos` / `x86_64-apple-macos`, `-isysroot <SDKROOT or ours>`, never `--sysroot`; links with rustup's `ld64.lld` through `-fuse-ld=lld`.
- [x] Environment: `SDKROOT` our sysroot and `MACOSX_DEPLOYMENT_TARGET` the lowest of rustc's (`--print deployment-target`), unless the user set them; without it cc-rs passes 10.7 for x86_64 off a Mac.
- [x] clang 18 or newer, checked before any download: the SDK's `TargetConditionals.h` fails on clang 14 ("KernelKit requires -fdefine_target_os_macros").
- [x] Unit tests: flags, env, the tables, the SDK's layout, clang's version.
- [x] `scripts/pins.py` re-pins Zig from ziglang.org's `index.json`; `every_package_is_on_every_mirror` fetches a shared file once per mirror.
- [x] `scripts/e2e.py` checks the Mach-O files (the dylibs they load, the minimum macOS) and runs them on a Mac, x86_64 through Rosetta; CI runs them on `macos-latest`.
- [x] Checked here: tests/hello built in a Linux container, run on this Mac, ad-hoc signed.
- [x] readme (Features, Targets, How it works, frameworks), agents.md scope, the roadmap item.

## Not here

- C++ for Apple: Zig's source has no stub of macOS's libc++ (Zig builds its own from source), and C++ is its own item. `-lc++` fails to link.
- Frameworks (`-framework Security`, `CoreFoundation`, …) fail with `framework not found`: the user's own `SDKROOT`, Xcode's SDK, or a macOS runner covers them.
- `-lresolv`, `-lz`, `-lobjc`: not in Zig's stubs; a crate that links them needs the user's SDK.
- clang run with no macOS version, as a configure script may when its flags aren't cc-rs's: our `--target` has none, so clang takes 10.4 and ignores `MACOSX_DEPLOYMENT_TARGET`; for x86_64 it then links `crt1.o`, which the SDK lacks. rustc and cc-rs pass the version, so their links and objects get it.
- The SDK's version in a binary is its minimum macOS, as with no `SDKSettings.json`.

## Result

tests/hello (ring, aws-lc-rs, libc) built for both targets in an arm64 Linux container on this Mac, with rustc 1.100.0 and two clangs: Debian trixie's 19 and Ubuntu 24.04's 18.1.3, the one on `ubuntu-latest`. No warnings. The first setup took 42 s, rustup's rust-std and llvm-tools included; the build 1 to 1.3 minutes. Debian bookworm's clang 14 stops with "Apple's targets need clang 18 or newer" before any download.

Both binaries ran on this Mac (arm64, macOS 27.2) and printed `hello 10 72d208d85bb7b6d1 72d208d85bb7b6d1`, x86_64 through Rosetta. The arm64 one is ad-hoc signed by lld (`adhoc,linker-signed`, `codesign --verify --strict` passes); the x86_64 one is unsigned, as Apple's ld64 leaves it. Each loads only `/usr/lib/libSystem.B.dylib` and `/usr/lib/libiconv.2.dylib`; their minimum macOS is 11.0 and 10.12. The C objects cc-rs builds carry the same.

Zig's tarball is a 23 MB download, once for both arches; the SDK takes 8.1 MB on disk. The Windows host is CI's: rustup ships `ld64.lld.exe` in gcc-ld there too.
